# 目标

在保留现有自动调度 R2 上传的前提下，让 Web 端手动触发并产生最终结果的扫描/测试/测速任务，在「启用 R2 上传」且配置完整时，自动把当前结果的 Sub-Store 目标列表上传到配置的 Worker/R2 文件名（默认 `cfdata-targets.txt`）。上传失败只提示和记录，不影响任务结果。同时向用户澄清 GitHub 上传账号配置的入口与「自动上传」下拉框的关系。

# 范围

## 目录结构

### 修改

- `combined_refactor/session.go`：在 Web 手动任务的结果完成节点接入 R2 自动上传触发；复用会话内已有结果，不改变任务生命周期。
- `combined_refactor/r2.go`：补充手动任务结果到 Sub-Store 目标列表的内容构建与上传封装，复用现有 `uploadR2Content` 的重试、超时、代理与脱敏行为。
- `combined_refactor/scheduler.go`（或等价配置读取位置）：提供当前 R2 配置的安全读取入口，供手动任务触发使用。
- `combined_refactor/index.html`：在「自动化」区块补充说明文案，指明 R2 自动上传同时覆盖自动调度与手动任务，且结果页「⬆ 自动上传」下拉框只用于 GitHub 账户。
- `combined_refactor/*_test.go`：补充手动触发、未启用跳过、配置缺失、空结果、上传失败与调度路径不重复上传的测试。
- `docs/comet/changes/manual-scan-r2-upload/specs/manual-scan-r2-upload/spec.md`：本 change 的完整目标规格。

### 不修改

- 不改变自动调度扫描的 R2 上传流程、内容格式、文件名与触发时机。
- 不改变 R2 Worker 协议、重试次数、超时、管理面代理与 token 脱敏规则。
- 不改变 GitHub/edgetunnel 上传逻辑与其账号存储方式。
- 不改变扫描、测速核心算法与现有导出格式。

## 现状事实

- R2 配置字段为 `r2enabled`、`r2workerurl`、`r2workertoken`、`r2filename`，由「自动化」区块保存；Worker token 不回传前端，留空保存表示保留旧值。
- 现有 R2 上传只发生在自动调度扫描的 CLI 流水线中：`runScheduledScan` → `runOfficialPipeline`/`runNSBPipeline` → `writeCLIExportAndMaybeUpload`。
- Web 手动任务的结果保存在 `appSession`（官方：`scanResults`、`testResults`；非标：`nsbHeaders`、`nsbRows`），现有 GitHub 自动上传在 `test_complete`、`official_speed_complete`、`nsb_csv_complete`、`nsb_speed_complete` 后由前端触发。
- 页面「⬆ 自动上传」下拉框只列出保存在浏览器 localStorage 的 GitHub 账户；没有 GitHub 账户时只显示「关闭自动上传」，与 R2 配置无关。
- GitHub 账号配置入口位于扫描结果页的「导出」弹窗内（GitHub 账户、Token、仓库、分支、目标路径、提交信息），不在右上角设置菜单或「自动化」区块中。

# 非目标

- 不实现 R2 的 S3 直传、Worker 部署或新的存储协议。
- 不在结果导出弹窗中新增独立的「上传 R2」按钮。
- 不改变 GitHub 账户的存储位置（仍为浏览器 localStorage）。
- 不处理多实例并发调度或跨实例上传协调。
- 不重做「自动化」区块的布局与调度/R2 配置字段。

# 验收示例

- A1：启用 R2 上传且 Worker 地址、token 已配置时，Web 手动官方扫描完成详细测试后，系统自动把当前结果的 Sub-Store 目标列表上传到配置的 R2 文件名，并记录成功日志。
- A2：官方批量测速完成后，R2 同名文件更新为包含测速结果的目标列表；上传失败不影响测速结果展示。
- A3：非标扫描结果生成后，以及非标批量测速完成后，系统按同一规则自动上传当前结果。
- A4：未启用 R2 上传时，手动任务不发起任何 R2 请求，任务行为与现状一致。
- A5：已启用 R2 但 Worker 地址或 token 缺失时，系统跳过上传并给出明确提示，不阻塞任务完成。
- A6：R2 上传在重试后仍失败时，系统给出失败提示并保留 R2 旧文件，不改变扫描/测试结果状态。
- A7：自动调度扫描的 R2 上传行为、内容与触发时机保持不变，且手动触发不会与调度路径重复上传。
- A8：页面「自动上传」下拉框仍只列出 GitHub 账户；R2 自动上传由「启用 R2 上传」开关控制，页面文案明确说明两者关系。

# 约束与不变量

- 手动任务上传内容始终为 Sub-Store 目标列表（`host[:port]#alias`），文件名取 `r2filename`，为空时使用 `cfdata-targets.txt`。
- 上传必须复用现有管理面代理传输，日志与错误信息不得出现 worker-token 明文。
- 上传失败、配置缺失或空结果不得改变任务状态、不得阻断后续上传或覆盖 R2 旧文件。
- 自动调度扫描的现有 R2 上传必须保持不变，手动上传不得与其共享触发导致重复请求。
- 手动任务的 R2 配置读取必须与「自动化」区块保存的配置一致，保存后无需重启即可生效。
